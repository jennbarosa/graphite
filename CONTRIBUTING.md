# Contributing to Graphite

Thanks for helping. Graphite is small, and most useful changes are a focused fix, a
test, or a clearer error message.

## Before you start

For anything bigger than a bug fix or a small change, open an issue first to discuss
the approach. This keeps the core small and avoids work that won't be merged. The core
deliberately knows nothing about games, animation, or workflows. Domain concepts belong
in annotations, front ends, or hosts.

## Setup

You need:

- Rust 1.88 or newer (edition 2024)
- [Bun](https://bun.sh) 1.x for the TypeScript runtime and its tests. CI pins 1.4.4
- TypeScript (`tsc`) 5 or later, for the type-check test. CI uses 6.0.3. Set
  `GRAPHITE_TSC` to its path, or put it on your `PATH`.

Build and run the tests from the repository root:

```sh
cargo build
cargo test
cargo test --no-default-features   # without the SIMD lexer
```

Several tests run TypeScript with Bun and fail with a clear message when Bun or `tsc`
is missing. `graphite doctor` reports which front ends can run here, and whether `tsc` is found:

```sh
cargo run -- doctor
```

## Checks before you open a pull request

CI runs these on every push and pull request. Run them locally first:

```sh
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo test --no-default-features
```

Clippy warnings fail the build, so fix them rather than adding `#[allow]` unless there
is a clear reason, and say that reason in a comment.

## Guidelines

- **Keep changes small and complete.** Fix the root cause, and update the callers,
  tests, and docs that the change affects.
- **Add a test for new behavior.** Parser changes usually belong in a fixture under
  `tests/fixtures/parser/`. The `.expected` files are hand-written, so update them by
  reasoning about the expected output, not by copying what the parser prints.
- **Keep the language out of the core.** Anything specific to one host language belongs in its
  front end. See [front ends](docs/front-ends.md).
- **Keep errors source-located.** Compile errors should point at the line and column
  that caused them.
- **Don't add dependencies for small helpers.** Check whether the standard library or
  existing code already covers the need.
- **Keep the docs in step with the code.** Update `README.md`, the page in `docs/` it
  affects, and `graphite help` text together. `tests/examples.rs` checks that every example
  graph still compiles, so a change to the language that breaks an example fails the build.
- **Keep the hot path allocation-free.** `tests/allocations.rs` enforces this for the
  step path. If you change it, run that test.

## Pull requests

- Branch from `main`, and keep each pull request to one logical change.
- Describe what changed and why. Link the issue if there is one.
- Make sure the checks above pass before requesting review.
- Commit messages use the form `type: what changed`, such as
  `fix: reject duplicate edge flags`. Keep the subject short, and don't add `Co-Authored-By`
  or other attribution trailers.

## Benchmarks

```sh
cargo bench --bench compiler_storage     # arena and interner
cargo bench --bench parser               # full DSL compilation
cargo bench --bench lexer                # tokenizer
cargo bench --bench frontend             # TypeScript emission
cargo test --test allocations            # allocation-count assertions
```

Set `GRAPHITE_BENCH_SIZE=small|medium|huge` (default `small`) and `GRAPHITE_BENCH_SEED`
(default 42). Inputs are generated from the seed, so a run can be reproduced. Do not run `huge`
on a busy machine.

This repository does not include measured results. Run the benchmarks on the machine you care
about. The huge TypeScript module is too large for `tsc`, as noted in the [roadmap](ROADMAP.md).

The parser fixtures in `tests/fixtures/parser/` are hand-written `.expected` decodings of each
`.graphite` file. They are not generated by the parser, so they check the output independently. To
inspect one case:

```sh
cargo test --test parser_fixtures walk -- --nocapture
```

## Repository layout

```text
src/
  lexer.rs, parser.rs      one-pass tokenizer and parser into compiled arrays
  graph.rs, arena.rs,      compiled graph data, arena, and string interner
  interner.rs
  frontend/                output front ends: typescript/ (index, chunks, runtime.ts)
  pipeline.rs              compile and write_modules
  bin/graphite/            the CLI; runtime_assets.rs bundles the TypeScript durable engine
src/frontend/typescript/durable/  durable engine, run log, and the run CLI (TypeScript)
cli/                       debugger session (TypeScript)
docs/                      user documentation
examples/                  DSL files, a TypeScript driver, a durable workflow, a Rust program
tests/                     Rust integration tests, fixtures, and Bun tests
benches/                   Criterion benchmarks
```
